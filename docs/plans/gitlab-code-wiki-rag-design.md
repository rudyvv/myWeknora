# GitLab 源码、技术 WikiPage 与 RAG 设计访谈

当前处于方案设计阶段，仅记录决定与证据，不实现功能代码。工作分支：`codex/gitlab-code-wiki-rag`。

## 已确认的范围

- 保留既有文档接入与加工能力，增加 GitLab 源码增量同步、可追溯技术 WikiPage、源码关键词和向量检索三项能力。
- 内网自建 GitLab，服务端可直接访问，允许保留仓库副本，并向现有生成与 Embedding 模型发送源码；接入身份只读。
- 每代码同步源对应一个仓库、一条指定分支和一个目标知识库；知识库可混合多个仓库与文档，检索支持限定仓库，阅读权限以知识库为准。
- 首期检索指定分支的当前已发布源码快照，引用固定到提交 SHA；暂不提供多分支或历史版本检索。
- 卡片按系统、模块和业务流程组织；源码双索引发布与 Wiki 生成分阶段完成，过期卡片默认不参与当前源码 RAG。
- 首期提供可选项目 Push Webhook、回调配置与连通测试；保留手动更新与默认每小时的可配置定时对账。部署时实际核验回调可达性和 GitLab 版本。
- 明确第三方库、压缩资产和确认的构建副本默认排除；生成代码分类标记后纳入检索，不主动为其大量生成卡片，Mapper SQL、接口和字段仍可作为业务证据。首次接入提供可调整的包含/排除预览。
- 全量源码建立索引，首批 Wiki 生成约 20–40 张系统概览、主要模块与核心流程卡片，显示覆盖清单并支持按模块补齐；该数量为验证批次目标，不是永久卡片上限。
- 首期静态关联常见业务链，不运行目标项目、不要求编译成功；不确定的动态关系明确标注。
- 技术卡片沿用既有文档 Wiki 的正文编辑、页面修订和回滚逻辑，不引入独立人工补充区或额外审阅发布流程。
- 源码获取采用受控服务端 Git 缓存与 REST 元数据管理，按需更新指定分支，固定提交后读取源码与计算差异；不执行目标项目。
- 源码块优先按方法、函数、Vue 区域与 MyBatis statement 组织，超大结构继续拆分，命中后按需补充类签名、注解与关联 SQL，并保留原文件位置。
- 可读文本在结构解析失败时降级切块，标记解析质量而不据此断言调用关系；无法可靠读取的文件明确失败，不能静默遗漏后将快照标为完整成功。
- 卡片的重要说明按段落或章节关联提交、路径、行号与符号证据，由模型引用已提供的证据编号、服务端核验代码位置。引用校验失败的卡片保留草稿并重试，不阻止已完成源码检索。
- 用户在 Q17 明确要求沿用既有 Wiki、RAG、Wiki+RAG 等 Agent 模式：源码接入现有 RAG 工具链，技术卡片接入现有 Wiki 工具链，由 Agent 模式/工具配置决定检索组合，不强制统一为一种检索入口。
- 用户在 Q20 确认采用 Tree-sitter 解析体系，优先验收成熟结构分块器；具体依赖版本、语言规则与执行位置另行确定。
- 用户在 Q21 要求参照原文档 Wiki 的受影响卡片更新逻辑；代码核查确认按来源关联及本次重新提取的卡片集合更新正文，技术卡片采用这一增量原则，源码依赖影响按 Q23 扩展，具体流程见整体方案。
- 用户在 Q22 确认引用点击优先打开 WeKnora 内的只读源码片段，展示固定提交、路径和原始行号，并提供同提交的 GitLab 外链；源码阅读继续遵循知识库及原文件范围权限。
- 用户在 Q23 确认变更优先沿代码证据与已知静态依赖定位受影响卡片；无法确定时扩大到所属模块，公共接口或公共配置变化扩展到关联模块与系统总览，新增文件重新检查模块骨架。
- 用户在 Q24 确认同源串行、允许跳过中间提交：正在加工的源码快照完成后追赶最新提交，合并尚未执行的 Wiki 更新；卡片写入前核验目标版本，旧任务不得覆盖新结果。
- 用户在 Q25 要求参照既有旧来源保留逻辑并据此决定。核查后采用现有 Wiki 修订保留窗口，并让仍被卡片、保留中的修订或运行任务引用的旧源码文件随引用保留；无引用的旧源码及旧检索产物可清理，不新增按天或完整 Git 历史的保留承诺。原文档流程本身不保证保存历史来源，此处为固定提交追溯所需的适配。
- 用户在 Q26 确认首期优先标准 Docker 部署，源码解析使用独立进程与专用资源额度；Lite 可连接同一外部解析服务，不要求随单应用发行内置全部解析运行时。
- 用户在 Q27 确认沿用现有 GitLab 数据源配置与凭据更新方式，每个代码同步源独立配置加密凭据；统一连接复用和批量轮换留待后续扩展。
- 用户在 Q28 确认暂停或移除连接保留已入库知识，另提供明确的“清除仓库知识”操作，清理该仓库源码、索引及历史证据，撤回其卡片贡献并保留其他来源支撑的内容。

- 用户在 Q30 确认首期以现有 PostgreSQL/ParadeDB 作为源码双索引验收基准，补充标识符、路径和符号匹配；仓库、权限及已发布快照范围在召回前限定，其他后端逐步适配，不为本功能新增搜索服务。
- 用户在 Q31 确认技术卡片按主题骨架、证据收集、正文生成、引用校验与独立 QA 执行，每张卡片最多自动修复两轮，瞬时失败重试共用累计调用/token/时间预算；耗尽后保留草稿、失败原因并支持手动重试，不阻塞源码检索。

## 代表仓库与首批语言

用户提供的统计基线：一个中大型 Java Web 仓库，包含 `nsb`、`evip-dashboard` 和 `evip_mobile`。全仓库约 5,126 个文本文件、171 万物理行；排除明显第三方库、压缩文件、构建产物等之后约 3,844 个文件、125 万行，后一个数字仍包含生成代码。Java 约 3,179 个文件、100 万行；JavaScript 约 888 个文件、38 万行；XML 约 464 个文件、23 万行；Vue SFC 约 60 个文件、9,800 行。各类型统计来自排除前的口径，不能直接相加视为最终入库规模。

用户授权根据上述信息确定首批语言与验证规模，并在后续反馈中明确将 TypeScript 与 Python 加入首批支持，据此选择：

| 内容 | 首期处理目标 |
| --- | --- |
| Java 8 | 首要源码结构解析：类、接口、方法、注解及原始代码位置，覆盖 Spring MVC 与 MyBatis 相关业务代码 |
| JavaScript | 前后端自有 JS 的源码结构解析，保留函数、模块及原始代码位置 |
| TypeScript | 类型声明、类、函数与模块的源码结构解析，具体 TSX 与新语法兼容性由选定解析器验证 |
| Python | 类、函数、方法、装饰器与模块的源码结构解析；增加独立语料验证，不能用 Java 代表仓库证明其覆盖 |
| Vue SFC（代表仓库为 Vue 2） | 识别组件与 template/script/style 区域，按 script 声明解析 JS/TS，引用保持原 `.vue` 文件位置；SFC 是复合文件格式，不作为独立编程语言计算 |
| MyBatis/Spring XML 与 SQL | 作为核心关联证据；识别 Mapper namespace、statement、配置节点及 SQL 原文，不因不是四种主语言而忽略 |
| HTML、JSP、FreeMarker、CSS/SCSS/Stylus、YAML、Dockerfile 等 | 保留检索与位置引用，按结构或文本边界切块并明确解析能力；首期不承诺所有嵌入语言的完整语义分析 |
| Kotlin | 代表仓库未发现源码文件，且用户未要求加入首批结构化解析目标 |

验证规模为一个完整代表仓库，入库范围上界按用户报告的约 3,844 个自有文件、125 万行规划。先用同仓库的一条业务链验证解析、引用与检索，再做全范围吞吐与增量验证；实际文件数、源码块数及成本必须在过滤与切块预览后统计，不由物理行数直接估算。

代表仓库没有 TypeScript 或 Python 源码，因此首批通用能力还需另加这两种语言的受控验证语料；不扩大代表仓库数量，也不假定 Java 仓库已验证所有语言。

上述语言选择已根据用户授权及补充要求确定；过滤原则、Wiki 首批覆盖、生成预算规则与试点链已确认，实际路径命中与产物统计在预览阶段确定。

本地只读抽查发现 `nsb/src/main/webapp/dist` 中存在业务与模板目录，不能仅按 `dist` 名称一律排除；该路径也可能含部署副本，需要按来源关系去重。部分 Java 文件超过 1 MB、Mapper XML 接近 800 KB，解析与切块应按符号或结构处理超大文件，不能把一个文件作为默认模型输入单位。

Q32 已确认试点：课表查询 `/wx/schedule/getPushSchedule.do`。前端 `evip_mobile/src/pages/User/ConfirmTimetable/index.vue:99` 请求此路径，`nsb/src/main/java/com/nsb/zy/controller/api/WxApiController.java:1210/1224` 调用 `service/provost/AttendanceServiceImpl.java:4839/4841/4853`，分别到 `dao/mapper/BusinessPushScheduleMapper.xml:293` 和 `BusinessPushScheduleDetailedMapper.xml:406`。请求拦截器与部署代理有前缀改写，关联提取应保留该配置证据或标为候选，不能把路径字符串近似匹配当作已验证运行行为。第二条问卷详情从 `evip_mobile/src/pages/ClassFeedback/detail/script.js:22` 到 `FreeTutorMobileController.java:265/281`、`FreeTutorServiceImpl.java:2597/2603` 及 `BusinessFreeTutorMapper.xml:1226`，并非仅凭目录名关联 ClassroomFeedbackService。

## 更新触发范围

用户授权根据实现难度确定 Webhook 是否进入首期。核查现有 Asynq 与调度后，计划首期提供可选的项目级 Push Webhook，并保留手动更新与定时对账；不在首期自动创建 GitLab Hook，不处理 MR、Issue 或 Pipeline 的独立内容同步。运行中的同源串行、重复提交幂等、后续提交合并与可恢复加工，无论是否采用 Webhook 都必须具备，因此不能把这些共同基础全部计为 Webhook 的额外成本。

Webhook 只作为检查指定项目与分支当前 HEAD 的信号，更新差异由已发布快照与目标提交计算，不能信任 payload 是完整提交或文件清单。GitLab 官方文档说明批量推送可不触发通知、提交数组也可能截断，因此定时对账保留。用户确认采用回调配置与连通测试、可达时启用 Push 触发、默认每小时可配置对账的方案；回调身份验证与实际 GitLab 版本兼容。GitLab 到 WeKnora 的实际可达性、Hook 配置权限和版本仍为部署时核验项，不能把对方案的同意当作连通性测试结果。

事实来源：[GitLab Webhooks](https://docs.gitlab.com/user/project/integrations/webhooks/)、[Webhook events](https://docs.gitlab.com/user/project/integrations/webhook_events/)、[Outbound request filtering](https://docs.gitlab.com/security/webhooks/)。当前未承诺分钟级加工完成。

## 技术卡片编辑与再生成

用户在 Q14 要求参照原有文档 Wiki 逻辑，因此复用现有标题、摘要和 Markdown 正文编辑，记录编辑来源、版本差异并支持回滚；编辑保存使用当前界面的版本冲突提示。技术卡片不增加独立人工补充区，不新增人工编辑后的候选版本审阅流程。

现有摘要页再入库替换正文，实体/概念页把当前正文与新增/撤回证据交给模型合并；自动更新不按人工编辑来源锁定正文，也没有逐段人工内容保护。因此“参照现有逻辑”意味着保留编辑与历史恢复能力，不意味着自动更新永远不会改动人工正文。源码快照、结构化代码证据及过期状态仍需适配，不能因为复用编辑界面而把页面版本等同于源码提交版本。

实现依据：`frontend/src/views/knowledge/wiki/WikiBrowser.vue:2894`、`internal/handler/wiki_page.go:461`、`internal/application/service/wiki_page.go:121`、`internal/application/service/wiki_ingest_batch.go:1839` 和 `:2047`。

追溯目标要求的适配：现有 `WikiPageRevision` 与 `revisionFromPage` 不保存 SourceRefs、ChunkRefs、PageMetadata，`RevertPageToVersion` 保留当前来源引用。技术卡片修订需要同步保存其提交版本与结构化代码证据，回滚正文时恢复对应证据并重新判断是否过期；否则历史正文可能错误地指向新版本代码。这是满足固定提交追溯所需的数据适配，不新增人工编辑方式或审阅步骤。历史证据保存与清理见整体方案第 9 节。

## 技术卡片的增量更新

用户在 Q21 要求参照原文档 Wiki，核查确认可采用“更新受影响卡片”的原则，而非每次提交重新生成所有卡片。现有文档流程以 `SourceRefs` 反查旧关联页面，重新提取更新文档中的候选实体/概念，按旧集合与新集合的并集生成页面更新：仍存在的实体/概念撤回旧贡献并合并新贡献，不再出现的条目撤回该文档来源，新条目创建或合入已有页面；文档摘要页直接覆盖。依据：`internal/application/service/wiki_ingest_batch.go:1239/1495/1532/1839/2047`，来源反查见 `internal/application/repository/wiki_page.go:497`。

复用的是页面来源对账、合并、编辑与修订机制；源码不能让每个源文件直接进入文档摘要/实体提取流程，否则会违背按系统、模块和业务流程生成首批 20–40 张技术卡片的已确认范围。原始源码的入库与技术主题规划分别执行，主题规划向页面更新提供相关文件、符号及代码证据集合。

Finalize 另外增量维护知识库 index 页简介，并对本批受影响页面清理死链、注入交叉链接；这不等于全库正文重生成。这里的 index 页是 Wiki 总览，不能与源码关键词/向量索引混淆。依据：`internal/application/service/wiki_ingest_batch.go:1067/1080` 与 `internal/application/service/wiki_ingest.go:2108`。

复用边界：现有关系粒度是文档 Knowledge 身份，不是源码符号、import、调用或 Mapper 依赖。源码增量需基于 Git 差异、卡片代码证据与可确定的静态关系选择受影响卡片；新文件和新入口还需评估模块骨架，不能只反查已有证据而漏掉新增能力。未受影响卡片需要完成当前快照适用性验证，保留原正文及原始证据提交，不能仅将 SHA 换成新提交就声称已验证；行位置变化也需复核。用户在 Q23 确认无法确定影响时扩大到所属模块，公共接口或公共配置变化进一步扩展到关联模块和系统总览。

真实删除行为需区分：删除文档的 cleanup 流程有单来源卡片删除、多来源卡片移除来源并排队撤回；但重解析时 `retractStale` 的 Reduce 路径没有明确的单来源删除分支，`wiki_ingest.go:2025` 的相关说明只是残留注释。因此不能宣称现有重解析已经完整实现无来源卡片自动删除。源码卡片失去有效证据时受既定过期过滤约束，不参与当前源码问答；来源确实被删除后撤回贡献，仅由删除来源支撑的页面按原来源删除规则清理，暂时生成失败不视为来源删除。完整流程见整体方案第 8–9 节。

删除流程证据见 `internal/application/service/knowledge_delete.go:222/247/260`，重解析只清待处理 ingest、保留现有页面见 `:317/331`。现有增量影响识别基于 SourceRefs，而不是 ChunkRefs 或修改行；文档级重新分析后才做页面级局部写入。当前 `mergeChunkRefs` 还会合并新旧块 UUID、仅撤回时不剔除旧 UUID（`wiki_ingest_batch.go:2125`）；代码证据需按来源版本替换并校验，不能直接将此并集当作可靠的当前证据。

连续提交处理按 Q24：每源仅有一个正在加工的源码目标，目标在开始后固定到 SHA；后续触发合并为待追赶的最新 HEAD，已开始的快照完成后再处理最新目标，不要求发布每个中间提交。Wiki 按当前已发布源码快照合并未执行更新，模型调用完成后的写入需检查目标版本，不能让旧任务覆盖更新后的卡片。执行租约、版本检查及失败恢复见整体方案第 6 节。

## 当前代码事实

- WeKnora 已有 GitLab connector 的 project/ref/path 配置与提交差异同步，但只允许文档类文件，读取和 URL 仍使用可变 ref，需补充源码加工与固定提交证据。
- 现有数据源 checkpoint 代表拉取/入队进度，不保证解析、索引或 Wiki 成功，不能直接作源码发布版本。
- 知识库的关键词、向量与 Wiki 开关独立，允许同知识库绑定多个数据源。
- WikiPage 已有目录、修订和 SourceRefs/ChunkRefs，但现有生成是文档级摘要、实体、概念；未发现人工正文的自动更新保护门禁。
- Wiki 搜索已有独立工具；不能仅凭 `wiki_page` 块类型及 boost 假定 Wiki 已具备同管线向量索引写入。
- 已有 Asynq 调度和并发池，但手动、定时、Webhook 的同源串行及持续提交合并仍需设计；数据源 GitLab Webhook 当前未实现。
- OpenWiki 可借鉴组件骨架、代码与测试证据、影响计划及独立 QA；它没有提供可移植的源码 AST 切块和双索引引擎。

后续核查补充：工作区 `.env` 的两个非敏感驱动字段为 `DB_DRIVER=postgres`、`RETRIEVE_DRIVER=postgres`，Compose 默认也是 postgres；这只是文件配置，未连接实际运行环境核验。现有 Postgres 后端支持 ParadeDB 关键词与向量检索，两路在召回 LIMIT 前可按知识库、Knowledge 身份和 tag 限定范围；共享检索参数与索引行尚无代码同步源/已发布快照字段，结果里的 Chunk metadata 不能替代召回前版本范围过滤。用户在 Q30 确认以此为首期验收后端。

GitLab 异常补充事实：当前 compare 仅传 from/to，没有显式祖先检测；compare 报错或 timeout 后重新枚举当前文件，不形成完整 keep 清单与消失文件对账（`internal/datasource/connector/gitlab/client.go:262`、`connector.go:294/330`）。分支 HEAD 或项目鉴权失败作为普通错误返回；流式逐文件更新已生效部分不能整体回滚（`internal/application/service/datasource_service.go:1430`）。源码模式需要独立快照清单与发布切换，不能照搬这些行为后宣称失败仍保留上一完整可用版本。

既有 Wiki 有并发、批次及单次输出 token 控制，但不能视为技术卡片的总生成预算。`MaxPagesPerIngest` 在类型与前端配置中存在，当前生产服务未发现读取使用，不能依赖该字段就声称页面上限已经执行。OpenWiki 骨架 critic 明确最多两次评审，正文问答 QA 则要求对未通过项继续重试；本地提示词未给该循环总轮次。源码卡片需另行确定有上限的生成、校验、修复及瞬时失败重试预算。依据：`internal/types/wiki_page.go:524`、`internal/application/service/wiki_ingest.go:179/190`、`references/openwiki/src/agent/prompts/code.ts:133/142`。

## 第三方源码解析库选型

用户要求优先评估成熟第三方库，不自建语言语法解析器。第一方资料调研已完成，结果记录在 `docs/plans/source-parser-library-research.md`；用户在 Q20 确认采用 Tree-sitter 解析体系，并优先验收当前 `xberg-io/tree-sitter-language-pack` 内置结构分块器，最终依赖版本尚未确认。验收重点包括原始内容与精确坐标、超大结构拆分及错误降级；固定运行时、语法与规则版本，并在构建阶段预装所需语法，避免内网部署首次运行再联网下载。成熟解析器负责语法结构、源码坐标与错误恢复；WeKnora 的适配层仍需负责框架关系、证据版本与入库接口，并在成品不满足要求时补足预算、超大结构拆分或坐标适配，不能把通用代码 splitter 当作已满足全部需求。Vue SFC 可复用 Vue 官方区域解析；MyBatis XML/SQL 通过成熟结构解析能力与项目规则关联，不自建完整语言语法。

性能结论必须基于代表仓库的基准验证：首次全量解析、少量文件变更、超大方法/Mapper、混合语言映射与降级比例；本次只调研、写文档，不安装依赖或编写验证代码。

## 首期解析与检索架构

Q29 确认独立 Python 源码解析服务，使用 Tree-sitter 解析体系及优先验收的 language-pack 成品分块器；Vue 使用固定版本官方 SFC 组件，在同一受控解析部署内提供 Node 辅助步骤。语言运行时、grammar 与规则在构建时固定并预置，分析任务不运行仓库构建或插件。Go 拥有 Git 凭据与缓存、知识库权限、同步运行状态、快照清单和索引发布职责；解析器只消费受范围约束的原始文件输入，返回结构化块、符号、原始区间、静态关系和质量，不转换为 Markdown 后交给通用文本 splitter。源码分析与普通 DocReader 任务分开容量管理，进程超时、取消及资源限额纳入部署。具体接口和初始并发预算在实现方案中明确，尚未安装或基准验证候选依赖。

Q30 确认 PostgreSQL/ParadeDB 作为首期完整源码验收后端，不新增搜索服务。现有关键词/向量召回、RRF 及可选 rerank 可复用；代码另需处理 CamelCase、snake_case、限定符号和仓库路径，保留完整标识符精确定位能力，不能仅依赖当前中文分词。仓库及已发布快照范围与原知识库/文件/tag 权限共同在召回 topK 前执行，不先检索所有旧版本再截断过滤；其他后端源码能力逐步适配，启用时应明确检查必需的范围与双索引能力，不能默默扩大范围。最终如何复用未变文件的块、向量与版本清单，在完整方案中说明。

## 技术卡片生成预算

Q31 确认技术 Wiki 按“主题骨架 → 证据收集 → 正文生成 → 引用校验与独立 QA”执行。主题仍按系统/模块/业务流程组织，首批约 20–40 张；覆盖清单可展示未生成、证据不足和待补齐主题，不把每个源文件触发成一张摘要卡片。

每张卡片首次生成并检查后，最多自动修复两轮；生成、检查、修复及瞬时失败重试共享累计调用/token/时间预算，任务恢复不得重置已消费额度。骨架规划与整批 QA 同样需要累计上限，不能通过另起子任务绕过预算。超过预算或证据仍不合格时保留草稿与原因，支持手动重试；手动重试启动新的有界尝试。引用位置校验与质量验证通过后才进入已就绪状态，不阻塞源码快照索引发布。具体数值适配实际模型输入/输出上限与速率额度，方案阶段不宣称既有配置已覆盖该总预算。

## 历史源码与证据保留

Q25 按用户要求核查既有实现后确定：沿用 Wiki 页面修订保留规则，而历史源码以实际引用关系保留。原文档重解析保留现存上传文件、重新生成块与索引，并不保存过去块作为可用历史来源；数据源更新还会删除旧 Knowledge、硬删旧条目后重新创建（`datasource_service.go:1399/1443`），知识删除清理旧上传文件（`knowledge_delete.go:562/573`）。现有 Wiki 修订不包含来源引用，回滚继续使用当前引用（`wiki_page.go:237/317`），因此其页面正文历史不能证明旧来源也被保留。

Wiki 修订的既有规则是按页面版本号窗口清理：自动生成及旧空来源修订适用 50 版本窗口，人工、Agent 和回滚修订可保留到所有来源都适用的 200 版本窗口；不是 50/200 天，也不是每种作者各保留固定数量。对应常量和裁剪条件见 `internal/types/wiki_page.go:348`、`internal/application/service/wiki_page.go:261` 与 `internal/application/repository/wiki_page.go:229`。删除页面时会硬删其修订（`wiki_page.go:412`），不增加独立归档入口。

源码适配规则：

- 保留当前已发布快照的全部纳入范围源码；暂存目标和正在运行的读取/生成任务保护自己使用的文件，直到完成、取消或失败清理。
- 当前卡片及尚未被现有规则裁剪的页面修订，保留其证据引用的旧源码文件与固定提交、路径及位置身份；同内容按租户内授权边界去重。旧文件作为不可变证据读取，不依赖 Git 分支 HEAD 或远端仍可访问。
- 历史证据的保留不扩大阅读权限，应用内阅读仍需满足当前知识库与源文件/tag 的授权范围；保留对象不能绕开权限适配直接暴露。
- 旧关键词/向量索引不因页面历史而长期保留；旧快照退出检索且相关读任务结束后可清理。历史文件仅用于引用阅读，首期不提供历史源码 RAG。
- 修订裁剪、页面删除及任务结束释放各自的引用；没有当前快照或其他有效引用的旧源码对象可回收。知识库删除按其范围清理页面、修订和源码引用，共享内容仅在无其他授权引用时删除。无法确认引用数时暂缓物理删除并重试，避免误删仍可阅读的证据。
- Git 缓存用于拉取与差异计算，不承担永久历史归档职责；清理缓存不能破坏已保留的代码证据。缓存和证据对象的容量、回收频率另行设计。

这复用既有有限修订历史与资源按 owner 引用释放的原则（`internal/application/service/knowledge_delete.go:55/75`），但现有资源 owner 没有 Wiki 修订类型，不能声称源码证据生命周期已实现。没有另设历史保留天数，也不保存每次提交的完整仓库副本。参见 ADR-0007。

## 部署与同步源管理

Q26 按标准 Docker 部署交付首期，源码解析由独立进程与专用资源额度执行；Go 继续负责同步编排、快照状态与索引发布。Lite 可选连接同一解析服务，无需把 Python、Node 与全部语法运行时打进现有单应用发行包。Q29 进一步确定 Python 服务及固定版本官方 Node SFC 组件，结构接口字段与流式传输细节在完整方案中明确。

现有 DocReader `Read`/`ReadStream` 返回 Markdown、图片与文件级 metadata，不能表达原始代码区间、符号和结构关系；当前 gRPC 还共用线程池。因此不能仅新增一个文档 parser engine 就视作源码管线完成。标准部署虽已有独立 docreader 容器，但没有仓库快照共享目录；源码专用接口的内容传输、只读路径范围、超时与并发需适配，不挤占普通文档读取容量。代码事实见 `docreader/proto/docreader.proto:7/46`、`docreader/main.py:296`、`docker-compose.yml:398/415`。

Q27 沿用现有每数据源 `base_url`、`access_token` 的加密配置及凭据更新入口（`internal/datasource/connector/gitlab/connector.go:23/31`、`internal/types/datasource.go:535`、`internal/application/service/datasource_service.go:246`）。源码同步仍用只读接入身份，不改变已确定的知识库阅读权限；凭据不交给生成模型或源码解析器。

Q28 管理行为区分“停止连接”与“清除知识”。原 `DeleteDataSource` 只删除同步源、移除计划与取消同步运行记录，并不删除已入库 Knowledge（`datasource_service.go:330`）。代码同步源复用这一产品行为，已保留快照和卡片继续按知识库权限可读；暂停/解绑后的回调及旧任务不得复活同步源或覆盖已清理内容，具体取消与写入保护由执行机制实现。

明确清除仓库知识时按代码同步源范围删除源码和检索产物、释放历史证据与缓存引用，并从多来源卡片撤回该仓库贡献；仅由该源支撑的页面可沿用原来源删除逻辑清理。清除包含该仓库的历史引用，不可因旧修订仍有 pin 就永久阻止管理员清除；多来源页面的修订与正文需要一起对账，保留其他来源独立支撑的内容。清理失败应可恢复，不允许陈旧任务重新入库；持久化与历史清理建议见整体方案第 6、9 节。

## 代码复核补充决策（Q36–Q37 已确认）

Q36 已确认：Git 管理的源码原文和块只读，拒绝普通文档的正文编辑/回滚、块开关、普通重解析、跨库移动/复制及直接删除源文件。标签和描述继续管理；重新加工走源码任务，移除文件走排除规则与新快照，目标库另建同步源。现有 Text 块编辑可修改正文，普通重解析会先清旧资源（`internal/application/service/chunk.go:405`、`internal/application/service/knowledge_process.go:2542`），与固定证据和完整发布的约束冲突，需要所有写入口适配。技术 Wiki 正文仍保留既有编辑和修订能力。

Q37 已确认：含源码贡献的技术页只有全部正文来源均满足 KB 和本次仓库/文件/tag 范围时才整页返回；首期不自动裁剪混合段落。仅选少数文件时可用源码 RAG，或扩大到模块/仓库范围读 Wiki。现有 Wiki 任一 SourceRef 命中即可读整页（`internal/agent/tools/wiki_tools.go:269/303/568`），不是严格内容范围；新增规则需覆盖正文、摘要、关联摘要、目录和历史读取，普通文档 Wiki 保持原行为。两项决策见 [ADR-0009](../adr/0009-git-managed-source-and-wiki-scope.md)。
