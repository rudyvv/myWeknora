## Implemented behavior

- Source-mode data sources default to an hourly schedule while retaining an explicit configured schedule. Manual and scheduled source triggers register in PostgreSQL before delivery; enqueue failure leaves the run queued for scheduler reconciliation.
- Per-source state tracks configuration generation, pending latest trigger, active run, expiring owner lease and monotonic fencing token. Duplicate/stale queue deliveries are no-ops; config edits, credential changes, credential clearing and source deletion fence active work before the source mutation.
- Cron registration remains restricted to active sources, while startup and 30-second reconciliation enumerate persisted source retry work independently of cron eligibility. Discovery includes queued legacy source logs created before coordinator state existed; document-mode legacy logs are not adopted. Error sources can recover queued manual retries without a new schedule; pause fences running and queued source work, and deleted, disabled, or explicitly canceled triggers are not revived.
- Before choosing the current content-mode pipeline, `ProcessSync` validates generation-bearing source deliveries against the persisted source mode, config fingerprint, coordinator generation and delivery generation. A stale source task cannot fall through into the document pipeline after a source-to-document switch. The pre-coordinator source queue format had no generation field, so a source-to-document pre-write fence also cancels its queued legacy logs, and canceled legacy wake-ups are no-ops.
- Result writes lock coordinator state before the sync log, then revalidate the active run, generation, fencing token, lease owner and expiry under those locks. Claim, registration and recovery verify persisted datasource identity/config instead of using a stale caller snapshot to advance generations. If a pre-write config fence is followed by a failed datasource write, the coordinator is restored from the persisted datasource row.
- While B is active, C is replaced by D as the single pending catch-up run. B can publish; release then dispatches D.
- Source runs persist their fixed target SHA and phase. Existing snapshot members, parse artifacts, staged chunks and embedding artifacts allow retry/restart to reuse completed work. Expired leases are fenced and re-dispatched.
- Snapshot publication, published pointer, last-success timestamp, run phase and a `source.wiki.update` outbox row are written in one PostgreSQL transaction. A startup and 30-second relay validates source/KB identity, lifecycle, configuration generation and current publication before atomically accepting a typed `source:wiki:update` / `knowledge_base` / `published_snapshot` `task_pending_ops` row and acknowledging the outbox. The payload is reconstructed from persisted records and carries schema version and stable event ID. Event acceptance is idempotent; superseded/deleted/cleared events do not recreate work. Relay failures stay pending with an attempt count and exponential retry backoff capped at five minutes. This is durable pending Wiki work only: it does not invoke generic `wiki:ingest`, enqueue an unregistered Asynq task, or claim that Wiki pages were generated; T15/T16 own the consumer and generation.
- A successful same-target no-op revalidates the current source, lease, KB, publication pointer and complete snapshot. If credential rotation superseded an undelivered outbox event, it restores the event at the current generation. `EventID` remains the stable publication identity; `DeliveryID` deterministically identifies `(EventID, ConfigGeneration)` and is the `task_pending_ops.dedup_key`. If relay already delivered an older generation, its pending/claimed operation row, payload and claim are left untouched; the current generation is inserted as a distinct durable row. An old consumer's ID-based acknowledgement can therefore remove only its old row. Once the delivered outbox is at the current generation, a same-generation no-op does not recreate a pending-op row already consumed by its consumer; relay retries remain idempotent on `DeliveryID`. Neither path revives work after deletion, credential clearing, source-mode disablement, publication replacement or permission/lifecycle invalidation.
- T15/T16 consumer handoff contract: use and durably remember `DeliveryID` as the per-generation idempotency/ack key so a same-generation notification re-enqueued after queue-row consumption cannot duplicate Wiki writes. Before any Wiki write, revalidate the source config generation, current published snapshot and current Wiki/source permissions. Reject stale-generation/stale-snapshot deliveries without writing Wiki, and acknowledge only the claimed pending-op row(s), never a newer row by publication `EventID`. `EventID` remains useful for grouping deliveries of one publication. T06 only persists these notifications; it does not implement Wiki generation.
- Durable `source_sync_runs.phase` is included as `source_run_phase` in public sync-log responses. The UI distinguishes initial queued delivery, waiting for catch-up, retry wait, and hard failure in the history drawer and latest-run control, with translations in all shipped locales. It continues polling queued/running runs, permits another source-mode trigger to become the latest catch-up request, and exposes the last successful publication in source-run details.
