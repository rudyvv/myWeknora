## Implemented behavior

- Source-mode data sources default to an hourly schedule while retaining an explicit configured schedule. Manual and scheduled source triggers register in PostgreSQL before delivery; enqueue failure leaves the run queued for scheduler reconciliation.
- Per-source state tracks configuration generation, pending latest trigger, active run, expiring owner lease and monotonic fencing token. Duplicate/stale queue deliveries are no-ops; config edits, credential changes, credential clearing and source deletion fence active work before the source mutation.
- Cron registration remains restricted to active sources, while startup and 30-second reconciliation enumerate persisted source retry work independently of cron eligibility. Error and paused sources can recover queued manual retries without receiving a new schedule; deleted, disabled, or explicitly canceled triggers are not revived.
- Result writes lock coordinator state before the sync log, then revalidate the active run, generation, fencing token, lease owner and expiry under those locks. Claim, registration and recovery verify persisted datasource identity/config instead of using a stale caller snapshot to advance generations. If a pre-write config fence is followed by a failed datasource write, the coordinator is restored from the persisted datasource row.
- While B is active, C is replaced by D as the single pending catch-up run. B can publish; release then dispatches D.
- Source runs persist their fixed target SHA and phase. Existing snapshot members, parse artifacts, staged chunks and embedding artifacts allow retry/restart to reuse completed work. Expired leases are fenced and re-dispatched.
- Snapshot publication, published pointer, last-success timestamp, run phase and a `source.wiki.update` outbox row are written in one PostgreSQL transaction. A startup and 30-second relay validates source/KB identity, lifecycle, configuration generation and current publication before atomically accepting a typed `source:wiki:update` / `knowledge_base` / `published_snapshot` `task_pending_ops` row and acknowledging the outbox. The payload is reconstructed from persisted records and carries schema version and stable event ID. Event acceptance is idempotent; superseded/deleted/cleared events do not recreate work. Relay failures stay pending with an attempt count and exponential retry backoff capped at five minutes. This is durable pending Wiki work only: it does not invoke generic `wiki:ingest`, enqueue an unregistered Asynq task, or claim that Wiki pages were generated; T15/T16 own the consumer and generation.
- The UI polls queued/running runs, permits another source-mode trigger to become the latest catch-up request, distinguishes queued from running, and exposes the last successful publication in source-run details.
