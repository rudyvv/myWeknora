# Spec：GitLab 源码接入、技术 WikiPage 与源码 RAG

状态：用户已确认整体方案、Spec、测试入口与 22 项 ticket 拆分，批准发布并实施。已发布：[Spec #8](https://github.com/rudyvv/myWeknora/issues/8)。

## Problem Statement

团队需要把内网 GitLab 中的中大型业务仓库纳入 WeKnora，既能理解系统、模块和业务流程，也能直接定位实现代码。现有文档接入与 Wiki 加工缺少源码结构、固定提交位置、完整版本发布和代码依赖影响能力，直接把代码当普通文档处理会导致每文件摘要、版本混用、失效引用及范围外内容进入回答。

代表仓库采用 Java 8、Spring MVC、MyBatis 和 Vue 2，过滤明显第三方与构建副本后约有 3,844 个自有文本文件、125 万物理行，仍含部分生成代码。需要同时满足大仓库加工、持续更新、精确引用和既有知识库治理。

## Solution

管理员在既有 GitLab 数据源入口选择源码模式，指定项目、分支、目标知识库和路径规则，预览实际纳入范围后启动同步。WeKnora 使用只读接入身份获取固定提交，解析源码并建立关键词与向量索引；只有完整源码快照准备就绪才切换发布版本，失败继续保留上一完整版本。

技术 WikiPage 按系统概览、模块职责和业务流程生成，重要说明绑定固定提交、原始路径和行号。卡片独立于源码索引发布，增量更新受影响主题，历史正文保留相应代码证据。用户继续选择 RAG、Wiki 或混合 Agent，在应用内阅读只读代码片段，也可以打开 GitLab 同提交外链。

首期支持 Java、JavaScript、TypeScript、Python 结构解析、Vue SFC 区域解析及 MyBatis XML/SQL 关联。其他纳入范围的页面、模板、样式和配置可检索并追溯位置，不承诺完整嵌入语言语义。

## User Stories

1. 作为知识库管理员，我希望在既有 GitLab 数据源入口选择文档或源码模式，以便保留原文档功能并接入代码。
2. 作为知识库管理员，我希望指定一个项目、一条分支和一个目标知识库，以便明确每个代码同步源的边界。
3. 作为知识库管理员，我希望复用每数据源的加密只读凭据并能够轮换，以便持续连接内网 GitLab。
4. 作为知识库管理员，我希望配置前校验 GitLab、解析服务和知识库检索能力，以便尽早发现无法加工的环境。
5. 作为知识库管理员，我希望预览实际纳入、排除、生成、超大及异常文件，以便确认处理范围与成本。
6. 作为知识库管理员，我希望调整并保存包含/排除规则，以便不误排除目录名相似的业务代码。
7. 作为开发者，我希望生成实体、Mapper 和 Web Service 仍可检索，以便定位业务依赖，而不产生大量无用卡片。
8. 作为知识库管理员，我希望手动同步指定分支，以便主动接入最新内容。
9. 作为知识库管理员，我希望设置定时检查，以便漏掉通知后仍能追赶仓库变化。
10. 作为知识库管理员，我希望可选接入项目 Push Webhook，以便及时触发同一同步流程。
11. 作为知识库管理员，我希望重复通知不会产生并发同步或重复发布，以便降低重复加工。
12. 作为知识库管理员，我希望在连续提交时处理固定目标后追赶最新目标，以便任务能完成且不会永久落后。
13. 作为开发者，我希望更新期间仍能查询上一完整发布版本，以便避免只读到半个仓库。
14. 作为知识库管理员，我希望鉴权、分支、解析或任一路索引失败时保留上一可用版本，以便故障不清空知识。
15. 作为知识库管理员，我希望 force-push 和删除文件都能可靠对账，以便当前知识与实际仓库一致。
16. 作为知识库管理员，我希望看到检测 HEAD、处理目标、发布 SHA、阶段及最后成功时间，以便区分已拉取与已可检索。
17. 作为开发者，我希望查询 Java 类、方法、注解及 Mapper 语句，以便快速定位后端实现。
18. 作为开发者，我希望查询 JavaScript、TypeScript 和 Python 的函数、类及导入，以便复用同一接入能力处理常用语言。
19. 作为开发者，我希望 Vue SFC 的命中位置仍指向原 .vue 文件，以便直接定位脚本、模板和样式区域。
20. 作为开发者，我希望关联 Java Mapper、MyBatis XML 和 SQL，以便理解查询与数据访问。
21. 作为开发者，我希望关联前端 API、Controller、Service 和 Mapper，以便追踪核心业务流程。
22. 作为开发者，我希望不能确定的反射、动态分派及动态 SQL 被标记，以便不把推测当成运行事实。
23. 作为开发者，我希望超大方法、坏语法和配置文件仍有明确质量标记的可读块，以便降级时不悄悄丢失内容。
24. 作为开发者，我希望精确搜索标识符、限定名、Mapper ID 和仓库路径，以便关键词命中代码实际名称。
25. 作为开发者，我希望用自然语言检索实现代码，以便定位相关逻辑而不必知道准确符号名。
26. 作为开发者，我希望查看命中的签名、注解、相邻拆分块和关联 SQL，以便理解必要上下文。
27. 作为用户，我希望同一次问答和后续工具读取采用一致的源码快照，以便回答不混合更新前后内容。
28. 作为用户，我希望答案显示仓库、SHA、路径、行号、符号及解析质量，以便检查来源。
29. 作为用户，我希望在 WeKnora 内打开固定版本的只读代码片段，以便不依赖个人 GitLab 权限查看已获授权知识。
30. 作为用户，我希望打开 GitLab 同提交外链，以便使用自己的 GitLab 身份继续阅读。
31. 作为用户，我希望选择仓库、文件或标签限制查询，以便获得符合当前范围的结果。
32. 作为用户，我希望继续选择 Wiki、RAG 或混合 Agent，以便按问题需要调用已获允许的工具。
33. 作为用户，我希望先获得约 20–40 张重要系统、模块及业务流程卡片，以便理解代表仓库而不阅读所有源码。
34. 作为用户，我希望看到 Wiki 主题覆盖和未完成原因，以便知道哪些内容还没有生成。
35. 作为用户，我希望卡片的重要说明引用已核验代码证据，以便逐段追溯说明依据。
36. 作为知识库管理员，我希望引用或质量校验失败时保留草稿并可手动重试，以便不覆盖有效卡片。
37. 作为知识库管理员，我希望生成、检查和修复都有累计预算，以便模型失败或恢复不会无限消耗。
38. 作为开发者，我希望源码变更只更新受影响主题，以便控制成本并保留无关页面。
39. 作为开发者，我希望新增入口和公共接口变化能扩展影响检查，以便不漏掉新能力或跨模块变化。
40. 作为用户，我希望过期卡片明确标记且不参与当前源码回答，以便不会引用未验证适用的知识。
41. 作为用户，我希望编辑、查看修订和回滚技术卡片，以便沿用原 Wiki 体验并阅读相应版本证据。
42. 作为用户，我希望含源码贡献的整页只有全部正文来源都符合当前范围才可读取，以便卡片不会带入范围外正文或摘要。
43. 作为知识库管理员，我希望源码原文由 Git 管理，标签和说明仍可管理，以便保持证据完整并满足知识组织需要。
44. 作为知识库管理员，我希望通过排除规则移除文件，并在新快照生效，以便不会直接破坏当前版本或旧引用。
45. 作为知识库管理员，我希望暂停或解绑后保留已有知识，以便停止连接时仍可阅读已接入内容。
46. 作为知识库管理员，我希望明确清除某仓库知识及其历史引用，以便删除源内容且保留其他来源独立支持的知识。
47. 作为运维人员，我希望服务重启后恢复未完成同步和生成任务，以便避免卡死、重复发布或预算重置。
48. 作为运维人员，我希望用标准 Docker 离线部署受限资源的解析组件，并观察阶段耗时、内存与模型消耗，以便稳定处理代表仓库。

## Implementation Decisions

1. 保留文档接入；GitLab 增加文档/源码内容模式，旧配置默认文档。一个代码同步源绑定一个项目、指定分支与目标知识库，同库可混合多个仓库和文档。
2. 阅读以 WeKnora 知识库及当前文件/tag/仓库范围为准，不实时映射个人 GitLab ACL。管理员控制接入与分享；GitLab 外链仍由个人 GitLab 身份决定访问。
3. 服务端使用受控 Git 缓存获取分支，REST 负责项目元数据与接入验证。按固定 SHA 读取对象，不运行目标仓库构建、插件、脚本、过滤器或依赖安装。
4. 固定提交的完整文件清单记录纳入/排除及原因。分类策略可预览调整并版本化；不只凭目录名排除业务内容。生成代码可索引但减少主动卡片主题。
5. 子模块、LFS、编码或类型异常必须说明真实内容可获取性，不自动扩大到新仓库授权。未明确排除的应处理内容不可读时不发布完整成功。
6. 使用连续完整清单计算增删改；可确定 rename 延续文件身份，否则删除加新增。非祖先提交或差异不可用时做完整清单对账，旧清单是删除判断依据。
7. 加工幂等键包含源、SHA 和有效配置/加工版本，不能只比较 HEAD。过滤、解析或模型改变可触发同提交重新加工。
8. Go 拥有凭据、缓存、调度、权限、运行、清单、快照发布及索引职责。独立 Python 解析服务复用 Tree-sitter 成品解析/分块，固定版本官方 Node 组件解析 Vue SFC；不自建完整语言语法。
9. 用专用结构接口传受限原始文件、逻辑路径/hash、语言和加工配置，返回块、符号、位置、静态关系、质量及覆盖；解析服务没有 Git 凭据或任意服务器路径访问。
10. 构建时锁定并预装运行时、grammar 和规则，候选成品依赖必须验收原文覆盖、坐标、超大结构和错误降级。运行时不下载语法包。
11. Java、JS/TS、Python 按类/函数/方法等结构优先切块；Vue 保留整文件坐标；MyBatis 关联 namespace/statement/include/resultMap 与 Java Mapper。可确定框架关系需有证据，动态行为保持不确定标记。
12. 原始字节、编码、CRLF 和缩进保留。Tree-sitter 字节与 Node UTF-16 坐标必须映射回原文件，显示行号从 1 开始；不连续上下文分别引用，不用拼接文本冒充单一原文区间。
13. 超大结构继续拆分，可读但不可可靠解析的文本显式降级；不可读内容显式失败。正文 token 预算服从实际 Embedding 模型，并为索引头部与上下文留空间。
14. 初始约 800 token 目标块、2,000 token 正文上限属于验收前调参起点，按实际模型限制收紧；不承诺未经测量的性能倍率。
15. 源码有专用加工路由，复用可分离的索引、Embedding、存储和权限能力，不沿用普通文档清旧块、立即启用与每文件摘要/Wiki 的整个流程。
16. 数据模型覆盖代码同步源、运行、不可变快照、完整文件成员、稳定逻辑源文件、不可变文件版本/解析产物、类型化源码块、版本化静态关系、页面贡献/依赖及修订证据引用。
17. 产物复用包含内容和有效解析/切块/上下文版本；向量复用包含实际 embedding 文本、模型受控版本与维度。路径或签名改变不能只凭 blob hash 复用。
18. 触发持久化后领取，同源租约与单调 fencing token 保护写入。手动、默认每小时可配置检查和可选 Push Hook 进入同一串行流程；运行目标固定，等待触发合并为最新待追赶目标。
19. 运行阶段区分获取、扫描、解析、索引、准备与发布及失败/取消。源码切块和双索引完整后原子切换 published 指针；Wiki 独立生成，不阻塞源码发布。
20. staging 与旧版本通过发布成员限定读取，不能仅依赖普通 enabled 标记。发布事务核验完整清单、两路索引、租约与配置代数，同时登记可恢复的 Wiki 更新信号。
21. 已开始的目标可完成发布，再追赶最新目标；旧任务不得覆盖新 Wiki。重启恢复失效租约、任务信号和未完成阶段，不重置已消费预算。
22. PostgreSQL/ParadeDB 为首期验收后端；新增类型化代码检索字段，保留完整标识符并支持 CamelCase、snake_case、限定名、路径段和 Mapper ID，中文与代码分析不混同。
23. 关键词和向量两路在 topK 前限定 tenant/KB、授权范围、仓库与请求发布成员，复用既有融合及可选 rerank。其他后端通过能力验收后再启用源码模式。
24. 一次问答固定各源已发布快照，并覆盖搜索、grep、块列表、文件信息、分页、上下文、Wiki 来源阅读及引用输出。清除和当前权限变化仍优先于读取保护。
25. 源码原文与块禁止普通文档正文编辑/回滚、开关、重解析、直接删除和跨库移动/复制；标签与描述仍可管理。重新加工走源码运行，移除文件走排除规则和新快照，跨库接入另建同步源。
26. 沿用实际 AllowedTools 和既有三类 Agent。源码双索引与 Wiki 能力分别预检；不擅自改变现有能力开关、工具权限或把选择 Wiki Agent 当作关闭源码索引。
27. Wiki 主题以源和模块/主题键命名，不按同名符号误合并仓库。先组件/入口骨架与覆盖清单，再收集证据和生成正文，首批约 20–40 张并可按模块扩展。
28. 模型只使用服务端证据 ID。确定性校验核对 SHA/hash/原文区间与权限，独立 QA 检查说明支持度与不确定关系，失败保留草稿、不覆盖已就绪页面。
29. 每卡首次生成/检查后最多修复两轮；所有瞬时重试共享有限调用/token/时间预算，骨架和整批 QA 也有累计上限并包含子任务。建议起点最多 18 次卡片调用，最终数值按模型预检固定；手动重试是新的有界尝试。
30. 影响页来自变更证据及确定静态反向依赖；不确定扩展模块，公共接口/配置扩展关联模块及概览，新增文件检查主题骨架。未受影响页核验依赖和清单后可保持正文与原证据 SHA，并更新适用验证。
31. 页面写入核验源代数、目标快照与基础页面版本；并发编辑后读新正文重新合并并计入预算。沿用编辑/修订体验，不保证人工段落永远不被调整。
32. 含源码贡献的整页只有全部正文来源均满足 KB 和请求仓库/文件/tag 范围、来源完整可验证时才返回。覆盖正文、摘要、命中片段、关联摘要、目录与历史，不做自动段落裁剪；普通文档 Wiki 保持既有规则。
33. 修订保存与正文对应的来源、代码证据和验证版本，回滚一起恢复后判断适用性。沿用原 50/200 页面版本窗口；当前快照、当前卡片、保留修订及运行中任务保护原文资源。
34. 旧索引退出当前检索，不为页面历史无限保留；历史证据按引用保留固定文件版本，可不依赖 Git 缓存或远端提交存在。去重与回收保持租户/授权边界，不删除仍有有效 owner 的资源。
35. 暂停/解绑停止新同步并令旧写入失效，保留已有知识。明确清除先撤销可查询范围，再可恢复清理索引/原文/历史并撤回该源贡献；包含被清除源的历史修订删除，其他来源独立内容与未受影响修订保留。
36. Push Hook 仅验证并持久登记触发信号，按已登记租户/项目/分支路由；检查所部署 GitLab 支持的 secret/签名与事件，不能信任 payload 指定任意仓库。管理员配置 Hook，不自动创建。
37. 标准 Docker 交付独立限资源解析组件，Lite 可选连接同一外部服务；源码、文档、Wiki、Embedding 独立容量管理并遵守共享模型额度。
38. 源 UI 显示过滤预览、运行阶段、检测/目标/发布 SHA、质量计数、Wiki 覆盖、错误与最后成功时间。源码引用在应用内只读显示原始位置及同 SHA GitLab 外链。
39. 缓存、staging、原文和向量容量分别观察；不足时明确失败并保留可用版本，不截断后发布或误删受保护证据。日志不输出凭据或整份源码。

## Testing Decisions

1. 主测试入口建议为现有知识库/数据源公开 API 加上 Agent 工具公开调用，构建一套可重复的集成验收夹具，观察用户可见配置、运行、查询、页面及来源行为，不以私有函数或表字段组合定义成功。
2. 从现有数据源服务/Handler 行为测试、GitLab HTTP fixture、检索服务结果测试、Wiki 工具范围测试、Wiki 修订服务数据库测试及资源授权测试延续测试习惯。既有测试只是先例，不声称已经覆盖新功能。
3. 外部 GitLab、时钟、队列及模型使用可控边界替身；用本地 Git 夹具制造提交、rename、删除和 force-push，用实际固定解析运行时做结构/位置契约验收。不要 mock 内部解析结果来代替语言正确性验证。
4. 原子发布、租约并发、崩溃恢复和 BM25/向量范围必须用真实 PostgreSQL/ParadeDB 集成测试验证；轻量服务测试不能替代真实两路索引。查询计划与范围效果一起检查。
5. 使用受控模型响应验证正确证据、虚构引用、语义不支持、超预算、瞬时重试和并发编辑；业务验收另用真实已配置模型记录效果和消费，不执行目标仓库。
6. 统一身份/范围用多 tenant、共享 KB、多仓库、文件/tag、发布/旧/staging 数据构造混淆集。搜索、阅读、分页、补全、摘要、关联页、历史和普通写入口都不能绕过范围或原文管理。
7. 首个业务链为 getPushSchedule，随后验证 FreeTutor 问卷详情及复杂 SQL。人工确定 30 个问题：10 个符号/路径、10 个业务流程、10 个前端/SQL 关联；至少 27 个问题 top10 找到正确证据。
8. 引用验收要求仓库/SHA/原文路径/行号与真实原文一致，包括 Unicode、CRLF、编码转换、Vue UTF-16 映射及不连续上下文。重要说明有核验且语义支持的证据，动态关系明确不确定。
9. 专项故障覆盖任一路索引失败、不可读文件、坏语法、超大结构、分支/鉴权失败、重复/持续触发、worker 崩溃、租约过期、信号丢失、旧页面写入、清除及引用回收。
10. 原文档模式与 Wiki/RAG/混合 Agent 回归；TypeScript、Python 使用独立语料，代表仓库不存在这些语言不能算覆盖。
11. 最终按过滤预览处理约 3,844 个自有文本文件/125 万行，测量全量和 1/10/100 文件变化的耗时、峰值内存、块/token/模型消费，并与同预算文本切块基线比较。性能阈值依据真实部署记录固定。
12. 此 Spec 未执行这些新测试，也没有安装候选依赖、真实调用模型或取得性能结果；测试入口已由用户确认，作为 tickets 的共同验收约定。

## Out of Scope

- 多分支并行接入和历史源码 RAG；历史源码只用于保留中的引用阅读。
- 实时同步个人 GitLab ACL、自动创建 GitLab Hook、MR/Issue/Pipeline 内容接入。
- 执行目标项目、运行测试/构建、完整运行时调用图、动态行为确定性分析。

- 手工修改 Git 管理的源码正文、自动裁剪跨范围技术页、无限历史归档。
